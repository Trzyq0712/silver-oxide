## Project Overview

**silver-oxide** is a Rust implementation of a high-performance verification backend for [Silver/Viper](https://github.com/viperproject/silver), developed at ETH Zürich (Programming Methodology Group, supervisor: Jonas Fiala).

The project has two layers:

1. **Parser & translator**: parses Silver programs, builds an AST, and lowers them to VMIR (Viper Mid-level IR).
2. **Verification backend**: verifies VMIR using equality reasoning via the [`egg`](https://egraphs-good.github.io/) e-graph library, with Z3 as a fallback for obligations that exceed equality saturation.

The core research hypothesis is that *most* proof obligations generated by [Prusti](https://github.com/viperproject/prusti-dev) for unannotated Rust programs — particularly those involving struct manipulation — can be discharged via lightweight equality reasoning rather than full SMT solving, yielding significant performance improvements over Silicon.

Requires nightly Rust (`rust-toolchain.toml` pins `channel = "nightly"`).

## Architecture: Silver → VMIR → Verification

The pipeline lives across three top-level modules, mirrored in `src/`:

### 1. `src/viper/` — Parsing, AST & Type Checking

- `parser.rs`: PEG parser (`viper_parser::vpr_program(input)`) using the `peg` crate. Prioritizes legibility over performance.
- `parsed/`: the parsed (untyped) Silver AST, re-exported as `viper::parsed::*`. `ast_ext.rs` adds helper impls; `builtins.rs` holds built-in declarations.
- `typed/`: the typed AST produced by type checking (`ast.rs`), plus `Display`/`Show` rendering (`display.rs`). This is what translation consumes.
- `globals.rs`: `Globals` / `GlobalsCollector` — catalog of all top-level declarations.
- `interner.rs`: `Interner` / `IdentCollector` — identifier interning.
- `typecheck/`: Silver-level type checking — `typecheck_program` (entry), `TypeError`, plus the type `lattice.rs`.
- `walk.rs`: AST traversal trait.

### 2. `src/translate/` — Silver → VMIR Translation

Entry point: the free function `translate::translate(...)` in `mod.rs`, which consumes the **typed** AST (`viper::typed`) plus `Globals`/`Interner` and emits a `vmir::Program`. Type checking is done upstream in `src/viper/typecheck/`; do **not** add type-checking logic here.

Sub-modules:
- `method.rs`: lowers method bodies (statements, assignments, method-call inhale/exhale).
- `resource.rs`: lowers contracts (`requires`/`ensures`) and concrete predicate bodies into `vmir::Resource` declarations (named `method#requires` / `method#ensures`, predicate name for predicates). `lower_spatial_never` lowers a spatial assertion into a guarded inst stream + result tuple.
- `pure_exp.rs`: pure-expression lowering helpers.
- `errors.rs`: `TranslationError`.

### 3. `src/vmir/` — VMIR IR

`vmir::Program` holds a `TiVec<MemberId, Declaration>` and a `lasso::Rodeo<MemberId>` interner. Declarations:
- `Function` — Silver functions and predicates (and fields modeled as `Ref → Addr<T>`)
- `Resource` — reusable unit of proof. `body: Option<ResourceBody>` — `None` for **abstract** resources (e.g. abstract predicates), `Some(_)` for concrete ones. A `ResourceBody` is a list of guarded `Inst` + a result tuple `(HeapVal, Val)` (heap delta + boolean condition). Inhale = add delta + assume bool; exhale = subtract delta + assert bool. Inside the body, `HeapVal::Temp(0)` is the **caller-supplied ctx heap** (passed via `ResourceCall.ctx_heap`); body-emitted heap insts start at `HeapVal::Temp(1)`. This mirrors the val-slot convention where params occupy `Val::Temp(0..n_params)`. **Calling an abstract resource via `ResourceCall` is illegal** — the frontend uses the resource's auto-emitted `@addr` function for `acc(R(args), perm)` instead.
- `Method` — method bodies emitted for methods that have a Silver body. A method call inside a body lowers to: `ResourceCall(m#requires, args)` → `(h_pre, b_pre)`, then `HeapInst::Sub`, then `Assert(b_pre)`; followed by fresh return allocations, `ResourceCall(m#ensures, args ++ rets)` → `(h_post, b_post)`, `HeapInst::Add`, `Assume(b_post)`.
- `Domain`, `Adt`, `DomainElement`, `AdtConstructor` — domain/ADT stubs.

Every instruction is `Inst { pc: PathCond, kind: InstKind }`. The path condition is a list of `Lit { val: Val, polarity: bool }` over previously-emitted `Val`s, rendered `<e1, !e3, e5>` (polarity `false` prints as `!`). It constrains when side conditions of `kind` must hold (e.g., `acc` requires `perm ≥ 0`, `div` requires non-zero divisor) and gates any knowledge produced (e.g., chunk-merge equalities from heap union). Empty `<>` is the trivial guard. `InstKind` is one of:
- `Pure(Type, PureInst)` — produces a `Val::Temp`. Variants: `Fresh`, `Unary`, `Binary`, `Ternary`, `Deref(heap, addr)`, `Perm(heap, addr)`, `FunctionCall`. Field/predicate `addr` functions are ordinary uninterpreted `FunctionCall`s.
- `Heap(HeapInst)` — produces a `HeapVal::Temp`. Variants: `Acc { loc, perm }`, `Add(h, h)`, `Ternary(c, h, h)`. `Sub(h, h)` exists but is **method-body only** — illegal in resource bodies.
- `ResourceCall { resource, args }` — produces a **pair** `(HeapVal::Temp, Val::Temp)`: the called resource's `(delta, bool)`. Both temp counters bump. Target resource must have `body: Some(_)`. Abstract resources are uncallable.
- `Assume(Val)` / `Assert(Val)` — boolean side checks. **Method-body only.** Produce no temps. Rendered without `:=` (e.g. `<pc> assert eN`).

Instructions are SSA; an instruction has no explicit id. The `Val::Temp` / `HeapVal::Temp` indices are the running counters of `Pure`/`Heap` and `ResourceCall` outputs in the surrounding instruction stream (the two counters are independent).

### 4. `src/verify/` — Verification Backend

Entry: `verify::verify(analyzed: &vmir::AnalyzedProgram)`. Walks the declarations in dependency (topo) order: each `Declaration::Resource` is verified self-contained by `method::verify_resource` (well-formedness side conditions), producing a cached `ResourceCertificate`; each `Declaration::Method` is then verified by `method::verify_method`, grafting the cached certificates at call sites instead of re-walking resource bodies.

The reasoning engine is the [`egg`](https://egraphs-good.github.io/) e-graph. `verify/context.rs` holds the `VerifyContext` (live `EGraph<Symbolic, ConstFold>`, rewrite rules, certificate graft/`transplant`); `verify/lang.rs` defines the type-free `Symbolic` language; `verify/analysis.rs` the `ConstFold` analysis; `verify/rewrite.rs` the rewrite rules; `verify/heap.rs` the symbolic `Heap`/`Chunk`; `verify/viz.rs` the optional Graphviz e-graph snapshots (`SILVER_OXIDE_VIZ`).

**Z3 fallback** (planned, not yet wired): the `z3` crate is present and exercised only by the `z3probe` bin. The verification path is currently egg-only. Z3 is intended as the fallback for non-linear arithmetic and complex functional specs once equality saturation can no longer discharge an obligation.

## Verification Architecture

The pipeline is **Smart Frontend / Dumb IR**: the lowering pass does the heavy structural work (symbolic execution, permission tracking, heap routing) so the solver and the e-graph only have to discharge pure mathematical facts. VMIR is **SSA** and topologically sorted; an instruction's id is implicit — it is the instruction's position in the owning `Vec<Inst>`.

### 1. Syntactic heap framing (no SMT required)

The frontend maintains a symbolic state tracker — a `HashSet` of currently-available resource instances. Framing reduces to a **syntactic equality** check: at a use site requiring `r1(e0)`, the frontend looks for `r1(e0)` in the current state. If present, it emits the IR; if not, it raises a compile error. The SMT solver never sees a framing assertion.

### 2. Pure logic decoupled from heap state

- **No method declarations in VMIR (for now).** A method call is lowered by the frontend into an inhale of the callee's `#requires` resource followed by an exhale of its `#ensures` resource.
- **Heaps are reusable, not linear.** A `HeapVal` is a value, not a consumable token: a pure function or resource accessor may read the same heap any number of times. "Producing a new heap" only happens when an operation actually changes the heap (e.g. `acc`, `Add`, `Ternary`).
- **Booleans flow globally.** The boolean component of a resource is handled via global `Assert`/`Assume` at inhale/exhale sites; the IR only routes heaps locally.

### 3. Explicit path conditions (stateless IR)

VMIR has no stateful `Push`/`Pop` instructions. Every `Inst` is self-contained and carries its own `PathCond` — the exact conjunction of boolean literals required to reach it. This preserves pure data-dependency and makes the IR trivial to analyse, debug, and reorder. (Implementation: `src/vmir/resource.rs` — `Inst { pc: PathCond, kind: InstKind }`, `PathCond { lits: Vec<Lit> }`, `Lit { val: Val, polarity: bool }`.)

### Anatomy of an instruction

```rust
Inst {
    // id implicit — the instruction's index in its owning Vec<Inst>
    pc: PathCond,    // pc literals needed to reach this inst
    kind: InstKind,  // Pure(Type, PureInst) | Heap(HeapInst) | ResourceCall(_)
}
```

How the verifier drives the e-graph (push/pop strategies, ITE handling, goal destructuring) is intentionally not specified here; it will be settled as the backend lands.

## VMIR Design Goals

VMIR is the project's core contribution: a lower-level IR that decomposes Silver into explicit, minimal verification primitives ("verification machine code"). Key design principles:

- **Explicit permissions**: every heap access states its permission amount; no implicit `acc(x.f)` shorthands.
- **Desugared operators**: redundant logical/arithmetic operators are reduced to a core set (e.g. `p <==> q` → `p == q`, `p || q` → `p ? true : q`) to keep the equality engine's rewrite rule set small.
- **Fold/unfold as first-class instructions**: fold and unfold are preserved as explicit VMIR instructions. Desugaring them into inhale/exhale sequences proved too difficult to do soundly, so the backend reasons about them directly.
- **Explicit heap states**: every heap-modifying operation produces a new `HeapVal`; the `old` operator is eliminated by threading the appropriate heap state explicitly. Heaps themselves are reusable values, not linear tokens (Pillar 2).
- **Unified resources**: fields and predicates are both modeled as resources. Their associated snapshot ADT and address function are not emitted explicitly — `resource@addr` is an ordinary `PureInst::FunctionCall`; `resource@snap` is `PureInst::Deref` applied to that result. Method contracts (`requires`/`ensures`) are resources in the same sense.
- **Proof reuse**: resource well-formedness is established once and reused across call sites, avoiding the "copy-paste" redundancy of Silicon.

## Equality Reasoning & `egg`

The verification backend uses [`egg`](https://egraphs-good.github.io/) for equality saturation:

- Verification conditions are encoded as e-nodes; obligations are discharged by checking whether a conjecture and known facts land in the same e-class.
- Congruence closure is used to handle heap consolidation: when `x == y` is learned, `x.f` and `y.f` unify automatically, reducing permission merging from O(n³) to near-linear.
- Rewrite rules encode domain-specific identities (e.g. permission arithmetic, predicate fold/unfold equivalences).
- Quantifier instantiation (e-matching lifted out of Z3 into `egg`) is a stretch goal.

When equality saturation cannot discharge an obligation, the backend falls back to Z3. A key evaluation metric is how much overhead the `egg` pass adds in such fallback cases.

## Key Conventions

- **String interning**: all identifiers go through `lasso::Rodeo<MemberId>`; use `interner.get(name)` to look up an existing `MemberId`, `interner.resolve(&id)` to get the string back.
- **Type-safe indices**: `TiVec<MemberId, T>` — never index with a plain `usize`.
- **`derive_more`**: most AST/IR nodes derive `Display`/`From`/`Into` via this crate.
- **Nightly feature**: `#![feature(never_type)]` is used in `lib.rs`.
- **Resource naming**: method contract resources are interned as `"methodname#requires"` / `"methodname#ensures"`.
- **Resource accessors**: snapshot ADTs and address functions are not emitted as explicit declarations. `resource@addr` is an ordinary uninterpreted `PureInst::FunctionCall` (the field/predicate name resolves to a function returning `Addr<T>`); `resource@snap` is `PureInst::Deref(heap, addr)` applied to that result.
- **Implicit SSA id**: an instruction has no explicit id. A `Val::Temp(n)` / `HeapVal::Temp(n)` refers to the `n`-th `Val` / `HeapVal` produced by the surrounding instruction stream — counters are independent. `Pure` and `ResourceCall` bump the `Val` counter; `Heap` and `ResourceCall` bump the `HeapVal` counter; `Assume`/`Assert` bump neither.
- **Auto-emitted `@addr` and `@snap`**: the translator emits a `Declaration::Function` for every field and predicate address function, and a `Declaration::Domain` interned as `"P@snap"` for every predicate (the opaque snapshot type). A **field**'s address function is interned under the field's **bare name** (e.g. `f`) — `@`-suffixes are reserved for *generated* implicit members; a **predicate**'s address function is interned as `"P@addr"`. `acc(R(args), perm)` lowers to a `PureInst::FunctionCall` to that address function followed by a `HeapInst::Acc` on the resulting `Addr<…>`.

## Current State & Roadmap

### Done (Phase 1)
Pre-processing passes (parsing, macro inlining, Silver-level type checking, global resolution) and a typed AST (`viper::typed`). SSA-based method lowering; abstract predicates & fields; method-call inhale/exhale lowering. The egg backend verifies small programs end-to-end: resource well-formedness is proven once into a `ResourceCertificate` and grafted (proven e-class merges transferred, no re-saturation) at call sites.

### In Progress (Phase 2)
Predicates with bodies: concrete predicate bodies are now lowered (`emit_predicate` → `resource::lower_spatial_never`). Fold/unfold logic is the next step.

### Planned (Phases 2–4)
Following a **vertical development strategy** — each phase extends both IR lowering and backend reasoning together for a chosen feature set:

| Phase | Weeks | Focus |
|-------|-------|-------|
| 1 | 1–8 | IR design; abstract predicates & fields; SSA-based method lowering; e-graph permission tracking |
| 2 | 9–12 | Predicates with bodies; fold/unfold logic |
| 3 | 13–18 | Heap-dependent functions; conditional control flow (DAG CFGs) |
| 4 | 19–26 | Evaluation vs. Silicon; extensions (full specs, loops, magic wands, quantified permissions, quantifier instantiation in `egg`) |

### Evaluation targets
- **Soundness**: regression tests against Silicon on handwritten benchmarks (linked lists, Fibonacci, etc.) and Prusti-generated Rust programs.
- **Performance**: end-to-end verification time, solver time, e-graph saturation metrics (node count, time to saturation, peak memory), and fallback overhead.
